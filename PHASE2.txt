1. SUMMARY
-------------------------------------------------------------------------------

Phase 2 turns AIMOS from a speed-only scheduler simulator into a real-time
scheduling lab:

  * Jobs can carry a DEADLINE (an absolute tick by which they must finish).
  * Periodic real-time task sets can be generated (period T, run time C);
    each job gets the implicit deadline release + T.
  * Two classic real-time schedulers were added: EDF (Earliest Deadline
    First) and RMS (Rate Monotonic Scheduling).
  * Real cluster traces (Google 2011 task_events, Alibaba 2018 batch_task)
    can be imported and converted into dashboard workloads.
  * Deadline metrics (miss rate, lateness) are computed everywhere.
  * The dashboard shows live SLA breach alerts during Gantt playback,
    red outlines on jobs that missed, deadline metric cards, a Deadline
    Miss column in the comparison table, and an RMS/EDF schedulability
    verdict.
  * PPO and Hybrid were retrained with a deadline penalty, so the learned
    schedulers now understand deadlines too.
  * The dashboard got a light mode with a toggle button.


-------------------------------------------------------------------------------
2. WHY THIS OPTION WAS CHOSEN
-------------------------------------------------------------------------------

Three Phase 2 packages were considered: OS Realism, Green AI, and
Enterprise & Real-Time. Option 3 (Enterprise & Real-Time) was chosen
because it fits the existing code best:

  * EDF and RMS follow the existing scheduler pattern
    (SchedulerBase.select_process(ready_queue, cores, time)).
  * Deadlines are two optional fields on Process; the simulator loop did
    not need to change.
  * The per-tick trace already returned by /simulate was enough to drive
    live SLA alerts.
  * Everything new is visible in the dashboard.


-------------------------------------------------------------------------------
3. CORE CONCEPT: DEADLINES
-------------------------------------------------------------------------------

A deadline is the absolute tick by which a job must be complete.

  Met       completion_time <= deadline
  Missed    completion_time >  deadline, OR the job never completed
  Lateness  max(completion_time - deadline, 0); None if never completed
  Miss rate misses / (jobs that have a deadline)

Jobs with a blank deadline are ignored by every deadline metric and behave
exactly as in Phase 1. A deadline must be later than the job's arrival.

Where deadlines come from:
  * typed by hand in the Deadline column,
  * the RT presets (implicit deadline = release + period),
  * Auto Deadlines:  deadline = arrival + ceil(3 x burst)   (slack = 3),
  * Google trace scheduling classes (see section 6),
  * the Deadline column of an imported CSV.


-------------------------------------------------------------------------------
4. PERIODIC REAL-TIME TASKS (RT PRESETS)
-------------------------------------------------------------------------------

A periodic task (name, period T, worst-case execution time C, phase)
releases a job every T ticks; each job needs C ticks of CPU and must finish
before the next release (implicit deadline = release + T).

The backend expands a task set into individual jobs over TWO HYPERPERIODS
(hyperperiod = LCM of the periods, capped at 2000 ticks / 400 jobs). Each
job gets program = task name, period = T, deadline = release + T.

  Utilisation         U = sum(C_i / T_i)
  Liu & Layland bound n * (2^(1/n) - 1)   (0.780 for n = 3)

  On one core:
    * RMS is GUARANTEED to meet every deadline if U <= the bound.
    * EDF meets every deadline if and only if U <= 1 (EDF is optimal).
  On several cores the dashboard compares U / cores with the same bound;
  this is only a heuristic (and labelled as such).

Presets (frontend/src/components/InputPanel.jsx, RT_PRESETS):

  Preset          Tasks (T, C)                          U      Jobs/ticks
  RT Schedulable  sensor(8,2) control(12,3) logger(16,4) 0.750  26 / 96
  RT Overloaded   sensor(6,2) control(8,3)  logger(12,3) 0.958  18 / 48

  RT Schedulable: below the RMS bound, so EDF and RMS both meet every
                  deadline on 1 core.
  RT Overloaded:  above the RMS bound but below 1, so on 1 core EDF misses
                  0 of 18 and RMS misses 2 (P2 at t=12, P11 at t=36).
                  This is the textbook EDF-vs-RMS result.

"T=x" next to a program name in the workload table is the period of the
task the job came from. Only jobs from periodic tasks show it; RMS uses it.


-------------------------------------------------------------------------------
5. NEW SCHEDULERS: EDF AND RMS
-------------------------------------------------------------------------------

Both are preemptive and global: each tick, all ready and running jobs are
ranked and the top N (N = cores) run. A selected job that is already
running keeps its core; newcomers fill idle cores first, then preempted
ones. This avoids fake migrations (shared helper assign_keeping_cores).

  EDF (backend/simulator/traditional/edf.py)
    Rank key: (no deadline, deadline, arrival, pid)
    Soonest deadline first; jobs without a deadline run last in FCFS order.
    Dynamic priority. Optimal on one core.

  RMS (backend/simulator/traditional/rms.py)
    Rank key: (no period, period, arrival, pid)
    Shortest period first; jobs without a period run last in FCFS order.
    Fixed priority per task. Simple and predictable (avionics,
    automotive), but not optimal.

Without deadlines EDF behaves like FCFS; without periods RMS does too.
On several cores even EDF can miss at high load (the Dhall effect).

6. CLUSTER-TRACE IMPORT (GOOGLE / ALIBABA)
-------------------------------------------------------------------------------

File: backend/experiments/trace_import.py

Supported formats (CSV, no header, as published):

  google   Google cluster-data 2011, task_events table, 13 columns
           (timestamp in microseconds, ..., event type, user,
           scheduling class, ...). Events used: 0 SUBMIT, 1 SCHEDULE,
           4 FINISH. One task -> one job:
             arrival = SUBMIT, burst = FINISH - SCHEDULE, program = user.

  alibaba  Alibaba cluster-trace-v2018, batch_task.csv, 9 columns
           (task_name, instance_num, job_name, task_type, status,
           start_time, end_time, plan_cpu, plan_mem), times in seconds.
           Only status "Terminated". arrival = start_time,
           burst = end_time - start_time, program = job_name.

Format selector in the dashboard:
  Auto-detect  counts the columns of the first row: 13 = Google,
               9 = Alibaba, anything else = clear error.
  Google / Alibaba  forces that parser; a file in the other format is
               rejected ("Line 1: expected 13 columns, got 9").
  For a correct file, Auto-detect and the explicit choice give identical
  results. The selector changes nothing until a file is imported.

Downscaling (to_processes):
  1. Completed tasks only, sorted by arrival.
  2. A window of max_jobs (dashboard: 60) consecutive tasks.
  3. One time scale for durations AND arrival gaps: the 95th-percentile
     duration maps to 50 ticks (preserves the trace's shape).
  4. Bursts clipped to [1, 50] ticks (the range the RL models and LSTM
     were trained on).
  5. Optional load: arrivals compressed/stretched so offered load is about
     load x cores (dashboard: 0.9).
  6. Deadlines:
       Google scheduling class 3 -> arrival + 2 x burst
                               2 -> arrival + 3 x burst
                               1 -> arrival + 5 x burst
                               0 -> none (batch)
       Alibaba -> none (use Auto Deadlines afterwards), unless a slack
       is passed to the API.

The status line shows e.g.
  "Imported 60 of 73 tasks (alibaba) - 6.5 s/tick - 0 with deadlines".

Sample files (synthetic, no real data, generated by make_synthetic.py):
  backend/experiments/sample_traces/synthetic_google_task_events.csv
      -> 60 of 80 tasks imported, 31 with deadlines, 6 programs
  backend/experiments/sample_traces/synthetic_alibaba_batch_task.csv
      -> 60 of 73 tasks imported, 0 with deadlines, 8 programs

Effect on scheduling: the schedulers do not change; they are tested on
real, uneven workloads (few long jobs, many short ones, bursty arrivals,
recurring programs). FCFS suffers from long jobs blocking short ones;
SJF/SRTF and the Hybrid gain the most.


-------------------------------------------------------------------------------
7. THE PROGRAM COLUMN
-------------------------------------------------------------------------------

Program is an optional free-text label (max 24 characters) naming which
program a job is a run of. (It was introduced in the retraining just
before Phase 2 and reused by Phase 2.)

  Source                     Values
  Mixed/Compute/IO presets   build, shell, render, grep
  RT presets                 sensor, control, logger
  Google trace               user (anonymised ID)
  Alibaba trace              job_name (e.g. j_1005)
  CSV import                 a column named program, command, cmd or exe
  Hand-added rows            blank until typed

Used by: the Hybrid (its LSTM predicts a job's burst from the last 8
finished bursts of the same program) and the SLA alert text. All other
schedulers ignore it; RMS uses the period, not the program.

8. DEADLINE METRICS
-------------------------------------------------------------------------------

File: backend/simulator/metrics.py

  MetricsEngine.deadline_events(processes)
    One record per job with a deadline, sorted by time:
    {pid, program, deadline, completion, lateness, missed, time}
    time = the deadline tick (when a miss becomes certain); used to raise
    SLA alerts in playback order.

  MetricsEngine.deadline_metrics(processes)
    deadline_jobs, deadline_misses, deadline_miss_rate,
    avg_lateness (over completed deadline jobs, on-time = 0), max_lateness.
    All None (deadline_jobs = 0) when no job has a deadline.

  MetricsEngine.summarize() now includes these fields.

10. API CHANGES
-------------------------------------------------------------------------------

Existing routes
  POST /simulate   process fields deadline / period / program accepted;
                   response adds deadline_events, deadline metrics in
                   metrics, and "realtime" for periodic sets:
                   {utilisation, per_core_utilisation, rms_bound,
                    rms_guaranteed, edf_feasible, exact, num_tasks}
  POST /compare    EDF and RMS included; each result carries the deadline
                   metrics.

New routes
  POST /workload/periodic
       body {tasks: [{name, period, wcet, phase?}], horizon?, num_cores?}
       -> {processes, horizon, utilisation, rms_bound, ...}
       default horizon = 2 hyperperiods (max 2000)
  POST /workload/deadlines
       body {processes, slack}  -> processes with
       deadline = arrival + ceil(burst x slack) where missing
  POST /import-trace   (multipart)
       file, format = auto|google|alibaba, max_jobs, offset, load,
       num_cores, slack  -> {processes, format, stats}
       stats: completed_tasks_in_file, imported, seconds_per_tick,
              clipped_bursts, with_deadline, programs

All new routes validate input and return HTTP 400 with an error message.

12. DEADLINE-AWARE RETRAINING OF PPO AND HYBRID
-------------------------------------------------------------------------------

Goal: the learned schedulers should respect deadlines without losing
their turnaround performance.

New per-job features (backend/rl/env.py, BASE_FEATURES):
  has_deadline, deadline_slack (time left), urgency, overdue.
Hybrid extra feature (backend/hybrid/hybrid_scheduler.py):
  pred_laxity = time left - predicted remaining work (LSTM).
Observation size: PPO 97, Hybrid 137.

Reward per tick (backend/rl/reward.py, RewardEngine):
  r = -(jobs in system) / 10            (sum = total turnaround, Little's law)
      - 0.05 x context switches
      - 1.0  x deadlines missed this tick
      - 0.1  x jobs already past their deadline   (sum = 0.1 x lateness)
  Bookkeeping was checked against measured misses/lateness on 30
  workloads (exact match).

Training mix (sample_training_workload):
  15% periodic task sets (U 0.4-1.0 per core, horizon <= 300);
  of the rest, 45% get per-job deadlines (slack uniform 1.5-6);
  the remainder have no deadlines. Per episode that is 15% periodic,
  about 38% aperiodic with deadlines, about 47% without deadlines.
  (Periodic episodes are short, so their share of training STEPS is
  smaller than 15%.)

Checkpoint selection (backend/rl/train_ppo.py, ValidationCallback):
  score = turnaround / FCFS on 70 deadline-free validation workloads
        + miss rate on 30 deadline validation workloads.
  Logs: models/training_logs/{mode}_{N}c.csv

Sanity check: a hand-set "most urgent first" weight vector reproduces
EDF's miss rate exactly, so the policy can express EDF.

Training: 8 models (PPO and Hybrid x 1/2/4/8 cores), 5M steps each,
lr 3e-4 (PPO) / 1e-4 (Hybrid), gamma 0.995, rollout 4096, batch 512,
net [128,128], log_std -1.5. About 50 minutes with 8 runs in parallel.

Models: models/ppo_scheduler_{N}c.zip, models/ppo_scheduler_hybrid_{N}c.zip
(models.zip rebuilt). Previous turnaround-only models are archived in
models/archive_2026-11-21_turnaround_only/.

Key findings:
  * EDF meets every deadline on feasible single-core periodic sets
    (U <= 1), as theory says; RMS starts missing above its bound.
  * The Hybrid beats EDF on overloaded aperiodic workloads
    (1 core slack 3: 75.3 vs 79.9; 4 cores slack 3: 9.5 vs 11.1):
    under overload EDF keeps chasing doomed jobs (domino effect).
  * Weakness: 1-core periodic sets at U = 1.0 (PPO 7.4%, Hybrid 21.3%,
    EDF 0%). Visible on RT Overloaded: EDF 0/18, Hybrid 3/18.
  * Turnaround on deadline-free workloads is preserved (ratio to FCFS,
    1/2/4/8 cores): PPO 1.01/1.00/1.01/1.00, Hybrid 0.95/0.94/0.96/0.99.

14. LIGHT / DARK THEME
-------------------------------------------------------------------------------

A sun/moon button in the dashboard header switches themes. The choice is
saved in localStorage ("aimos-theme"); first-time visitors get their OS
preference. A small script in frontend/index.html applies it before first
paint (no dark flash).

Implementation:
  * frontend/src/index.css: all theme colours are tokens defined twice,
    on :root (dark) and :root[data-theme="light"]; Tailwind utilities
    (bg-card, text-mtx3, border-ink/10, bg-field ...) read them.
    Light mode uses darker accents for contrast, and remaps the
    -300/-400 status colours (red, emerald, yellow ...) to -600/-700.
  * frontend/src/lib/theme.js: useTheme() hook (theme + toggle) and
    useChartColors() for Recharts (colours are props, not classes).
  * Hard-coded dark colours in components were replaced by tokens
    (white overlays -> "ink", #12121e inputs -> "field").
  * Fix found on the way: the text-mtx1..5 classes were never generated
    (Tailwind 4 ignores tailwind.config.js), so all that text showed in
    one grey. They are now real theme colours in both modes.

18. KNOWN LIMITATIONS AND POSSIBLE NEXT STEPS
-------------------------------------------------------------------------------

  * Learned models still miss deadlines on 1-core periodic sets at full
    load (U = 1.0) where EDF misses none. Fix idea: more periodic sets in
    the training mix, or a stronger penalty near full load (~1 hour of
    retraining).
  * Multi-core schedulability is shown as a per-core heuristic, not an
    exact test.
  * Trace import takes the first 60 tasks only; .gz files and files over
    64 MB need manual preparation (could be automated).
  * Alibaba traces carry no deadlines; Auto Deadlines uses a fixed slack
    of 3 (not adjustable in the UI).
  * Nothing from Phase 2 is committed to git yet.
